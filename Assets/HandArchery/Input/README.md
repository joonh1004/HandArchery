# Hand input integration

Run `Tools/PrepareMediaPipe.ps1` before opening a fresh clone. It downloads the pinned official 0.16.3 archive once, verifies its size/SHA256, extracts the bundled model and licenses, and adds the local tarball reference. An already downloaded official archive can be supplied with `-ArchivePath`. `Packages/Local` is deliberately excluded from Git. No external service or runtime download is used.

Add `MediaPipeHandInput` to one scene object; consume it as `HandArchery.Core.IHandInputSource`. The component starts on enable and stops/disposes camera, model, image backing textures on disable. `Restart()` recreates the native task and opens the selected camera. Empty camera name uses the first enumerated device; a configured but absent name reports missing instead of silently changing cameras.

`TryGetLatest` can return the same captured frame repeatedly. A read never updates its sequence or capture timestamp. Every *processed* new camera image (including no hands) publishes one sequence. Stop/failure publishes an explicit untracked cancellation sample. The consumer must reject old timestamps and duplicate/previous sequences; the source does not invent fresh frames while a camera stalls.

Timestamps use `Time.realtimeSinceStartupAsDouble`, sampled before camera pixel read/inference. The synchronous MediaPipe VIDEO timestamp is monotonically increasing milliseconds. Pixel arrays, textures and native Images remain alive until detection returns; Images are disposed before the texture is overwritten. A `false` result means no hands and does not overwrite the upstream result list, so the adapter deliberately publishes two untracked hands instead of stale landmarks.

WebCamTexture bottom-up rows, `videoVerticallyMirrored`, and clockwise `videoRotationAngle` are corrected in `CameraPixelTransform` *before* inference. MediaPipe receives upright, unmirrored top-left rows. `HandCoordinates` converts landmark output exactly once to bottom-left viewport 0..1 and optionally mirrors X (default on). Aim is middle MCP landmark 9. Pinch ratio is pixel-distance(thumb tip 4,index tip 8) / pixel-distance(index MCP 5,pinky MCP 17), accounting for width/height. Invalid values, outside aim coordinates and degenerate palms are untracked.

Roles use MediaPipe label `Left`/`Right`, not the left/right half of the screen. `SwapHandedness` defaults on to compensate selfie-trained labels for unmirrored camera pixels; actual model/camera behavior must be calibrated with a physical left hand. The probe provides independent label-swap and X-mirror toggles. These controls have distinct purposes. The game may choose bow hand separately; this adapter always reports physical left/right after calibration.

`HandArchery > Create Input Probe Scene` builds a diagnostic scene that shows status, coordinate markers and pinch numbers only. It never shows, saves, screenshots or transmits raw camera images. The scene can stop/restart the input and inspect mirror/role settings. Use one physical left hand, then right, both, move up/right, pinch/open, hide/reappear, and verify labels and coordinates before judging real hand playability. Automated blank inference/camera stream checks do not verify that behavior.

Batch entry points: `HandArchery.Editor.HandProbe.ValidateContracts`, `.ValidateNative`, `.BuildWindowsProbe`. The Windows probe supports `--hand-probe-auto` for native initialization plus two 12-second camera cycles separated by stop/restart, with background updating enabled explicitly. Exit 0 requires blank inference plus at least five processed images and a frame age under one second in each camera cycle; exit 2 means native probe error, exit 3 means camera cycles did not both stream. It logs only status/counts/timing, never frames. `CameraStreaming` becomes false after half a second without a processed image; cached hand time/sequence stay unchanged. Human calibration and actual hand quality remain separate checks.

The label-swap default follows the [official legacy MediaPipe Hands selfie convention](https://github.com/google-ai-edge/mediapipe/blob/master/docs/solutions/hands.md); applying that convention to this Tasks model is a calibration assumption, not a verified physical-hand result for the current camera.

On the current USB CAMERA/Windows machine, a visible normal player passed continuous capture and stop/restart (139 and 145 processed frames over two 12-second cycles). Hidden-window and graphical-batch runs only received one then zero camera updates even while Unity kept updating, so those conditions are unsuitable for judging this camera's continuity. Actual hands/handedness/pinch calibration still require human testing. The optional `--hand-probe-camera-only` branch bypasses MediaPipe entirely for future isolation; that optional branch has not been executed here.
